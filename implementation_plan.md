## 1. Confirmed Decisions & Tech Stack

| Decision | Confirmed Choice |
|---|---|
| **Architecture** | Monorepo — single git repo, `client/` + `server/` folders |
| **Frontend** | React 18 + Vite |
| **Styling** | Tailwind CSS v3 + Lucide React (icons) + Radix UI (accessible primitives) |
| **State / API Client** | TanStack Query v5 (React Query) + Axios |
| **Backend** | Node.js v20 LTS + Express.js v4 |
| **Database** | MongoDB (local) via Mongoose v8 — connection string: `mongodb://127.0.0.1:27017/festops` |
| **Authentication** | Firebase Authentication — Google OAuth only (no email/password login) |
| **Session Bridging** | Firebase ID token (verified on backend via Firebase Admin SDK) → server issues signed JWT stored in HTTP-only cookie |
| **Schedule Import** | `.xlsx` files only (via `xlsx` npm package); manual form entry also supported |
| **Background Jobs** | `node-cron` — runs inside the Express process |
| **Notifications** | In-app only; stored in MongoDB; polled by frontend every 30 seconds |
| **Role System** | 4 tiers: `admin` (4th year/coordinator) > `senior` (3rd/2nd year) > `junior` (1st year) + system-level `superadmin` reserved for future use |
| **Deployment (MVP)** | Local development only; no cloud deployment in Phase 1–8 |
| **Monorepo Tool** | No Turborepo or Nx — plain npm workspaces in root `package.json` |

## 4. Firebase Authentication Setup

### What Firebase handles

- Google OAuth identity provider.
- Issuing Firebase ID tokens (short-lived JWTs) to the authenticated browser.

### What Firebase does NOT handle

- Application roles (`admin`, `senior`, `junior`).
- Any database operations.

### Complete Authentication Flow (Step by Step)

```
1. User clicks "Sign in with Google" on client Login page.
2. Firebase client SDK opens Google OAuth popup.
3. On success, Firebase returns a firebaseUser object with:
   - firebaseUser.uid  (string, unique Google account ID)
   - firebaseUser.email
   - firebaseUser.displayName
   - firebaseUser.photoURL
4. Client calls firebaseUser.getIdToken() to get a short-lived ID token.
5. Client sends POST /api/v1/auth/login with body: { idToken: "<firebase_id_token>" }
6. Backend auth.js middleware:
   a. Calls firebaseAdmin.auth().verifyIdToken(idToken).
   b. On success gets decodedToken with { uid, email, name, picture }.
   c. Looks up User in MongoDB by email.
   d. If User does NOT exist: creates new User record with role='junior', seniority='1st_year'.
      Admin must manually promote them after first login.
   e. If User DOES exist: loads their existing role and seniority.
7. Backend issues its own signed JWT:
   payload: { userId: user._id, role: user.role, seniority: user.seniority }
   signed with JWT_SECRET, expires in JWT_EXPIRY (7d).
8. Backend sets JWT as HTTP-only cookie:
   res.cookie('token', jwt, {
     httpOnly: true,
     secure: process.env.COOKIE_SECURE === 'true',
     sameSite: 'strict',
     maxAge: 7 * 24 * 60 * 60 * 1000
   })
9. Backend responds 200 with user object (no token in body):
   { _id, name, email, role, seniority, photoURL, isActive }
10. Frontend stores user object in AuthContext state.
    Frontend does NOT store the JWT. It is in the cookie automatically.
11. All subsequent Axios requests automatically include the cookie.
12. Every protected backend route reads the cookie, verifies JWT, attaches req.user.
13. On logout: Client calls POST /api/v1/auth/logout.
    Backend calls res.clearCookie('token') and responds 200.
    Client revokes Firebase token via firebase.auth().signOut().
```

### `server/src/middleware/auth.js` — complete implementation

```javascript
const jwt = require('jsonwebtoken');
const ApiError = require('../utils/ApiError');
const User = require('../models/User');

const protect = async (req, res, next) => {
  try {
    const token = req.cookies?.token;
    if (!token) throw new ApiError(401, 'Not authenticated. Please log in.');

    const decoded = jwt.verify(token, process.env.JWT_SECRET);
    const user = await User.findById(decoded.userId).select('-__v');
    if (!user || !user.isActive) throw new ApiError(401, 'User account not found or inactive.');

    req.user = user;
    next();
  } catch (err) {
    next(err);
  }
};

module.exports = { protect };
```

### `server/src/middleware/rbac.js` — complete implementation

```javascript
const ApiError = require('../utils/ApiError');

const ROLE_LEVELS = { admin: 3, senior: 2, junior: 1 };

const requireRole = (allowedRoles) => (req, res, next) => {
  if (!req.user) return next(new ApiError(401, 'Not authenticated.'));
  if (!allowedRoles.includes(req.user.role)) {
    return next(new ApiError(403, `Access denied. Required roles: ${allowedRoles.join(', ')}.`));
  }
  next();
};

const requireMinRole = (minRole) => (req, res, next) => {
  if (!req.user) return next(new ApiError(401, 'Not authenticated.'));
  if (ROLE_LEVELS[req.user.role] < ROLE_LEVELS[minRole]) {
    return next(new ApiError(403, `Access denied. Minimum role required: ${minRole}.`));
  }
  next();
};

module.exports = { requireRole, requireMinRole };
```

## 5. Role Hierarchy & Permission Matrix

### Role Definitions

| Role Enum Value | Display Name | Who Has It | Access Level |
|---|---|---|---|
| `admin` | Coordinator / Admin | 4th year members | Full system access |
| `senior` | Senior / Team Lead | 2nd and 3rd year members | Operational access |
| `junior` | Junior / Team Member | 1st year members | Read + limited write |

### `seniority` field (separate from `role`)

| Seniority Enum Value | Meaning |
|---|---|
| `1st_year` | Always mapped to `role: 'junior'` on creation |
| `2nd_year` | Can be promoted to `role: 'senior'` by admin |
| `3rd_year` | Can be promoted to `role: 'senior'` by admin |
| `4th_year` | Can be promoted to `role: 'admin'` by admin |

**Important:** `role` and `seniority` are stored separately. The application RBAC always checks the `role` field, never the `seniority` field directly. A 3rd-year person might still be `junior` until promoted.

### Promotion Rules

- Only `admin` can change another user's `role`.
- An `admin` cannot demote themselves if they are the only active admin.
- Every promotion/demotion creates an `AuditLog` entry with action `USER_ROLE_CHANGED`.

## 8. Core Service Logic & Algorithms

### A. Import Service (`importService.js`)

**Input:** `.xlsx` file buffer + festId
**Output:** Preview object (nothing saved to DB)

```
1. Read buffer: xlsx.read(buffer, { type: 'buffer' })
2. Get first sheet: workbook.Sheets[workbook.SheetNames[0]]
3. Convert to JSON array: xlsx.utils.sheet_to_json(sheet, { defval: '' })
4. Load all existing venues for festId from Venue collection.
5. Load all existing events for festId from Event collection.
6. For each row (1-indexed row number for user display):
   a. Check required columns: 'Event Name', 'Category', 'Date', 'Start Time', 'End Time', 'Venue'.
      If any missing or blank → classify as 'error'.
   b. Validate 'Date' as YYYY-MM-DD. If invalid → error: "Invalid date format. Use YYYY-MM-DD."
   c. Validate 'Start Time' as HH:MM. If invalid → error: "Invalid start time. Use HH:MM."
   d. Validate 'End Time' as HH:MM. If invalid → error: "Invalid end time. Use HH:MM."
   e. Validate parsed startTime < parsed endTime. If not → error: "Start time must be before end time."
   f. Check venue name against loaded venues (case-insensitive trim match).
      If not found → warning: "Venue not found. It will need to be created before committing."
   g. Check for existing event with same name and date in fest.
      If found → warning: "Duplicate event detected. Will not overwrite existing."
   h. Parse optional columns with fallback defaults:
      'Min Coverage (mins)' → default 15
      'Team Size' → default 2
      'Priority' → default 'medium'
      'Deliverables' → default []
      'Skills' → default []
   i. Classify row: 'error' (has errors, blocked from import), 'warning' (importable with caveats), 'valid'.
7. Generate previewToken = uuid(). Cache preview data server-side for 10 minutes (in-memory Map).
8. Return:
   {
     previewToken: string,
     totalRows: number,
     valid: parsedRow[],
     warnings: parsedRow[],
     errors: parsedRow[],
     summary: { valid: N, warnings: N, errors: N }
   }
9. At POST /import/commit:
   - Retrieve preview by previewToken. Throw 400 if expired or not found.
   - Filter rows by submitted rowIndexes (only valid and warning rows are committable).
   - For each row: look up venueId from venue name. Create Event document.
   - Return { created: N, skipped: N, events: [...] }.
```

---

### B. Assignment Scoring Engine (`assignmentEngine.js`)

**Function: `suggestAssignments(eventId)`**

```
1. Load event from DB including venueId, startTime, endTime, teamSizeRequired, requiredSkills, priority.
2. Load all active users (isActive: true).
3. Load all approved/suggested EventAssignments for the same festId and date.
4. For each candidate user:

   HARD CONSTRAINTS (score = null → exclude):
   a. Check user.availability for a slot where:
      - slot.festId matches event.festId
      - slot.date matches event.date
      - slot.isAvailable === true
      If no matching slot → exclude.
   b. Check existing assignments for this user on event day.
      For each existing: if startTime < event.endTime AND endTime > event.startTime → overlap → exclude.
   c. Travel feasibility:
      Find last assignment ending before event.startTime for this user.
      If found: load prevVenue. If (event.startTime - prevAssignment.endTime) < prevVenue.travelBufferMinutes → exclude.

   SOFT SCORING (base score 100, add/subtract):
   d. Skill match: +30 per matched skill between user.skills and event.requiredSkills.
   e. Workload penalty: count confirmed assignments for user today. -25 per existing assignment.
   f. Priority bonus: if event.priority === 'critical' AND user.seniority in ['3rd_year', '4th_year'] → +40.
   g. General seniority bonus: +20 for senior/admin role on high or critical events.

5. Sort candidates by score descending. Select top N (= event.teamSizeRequired).
6. For each selected candidate where seniority === '1st_year':
   a. Check if any OTHER selected candidate has seniority in ['2nd_year', '3rd_year', '4th_year'].
   b. If yes → set mentorId = that candidate._id.
   c. If no → set isMentorNeeded = true, mentorId = null.
7. Create EventAssignment docs with status: 'suggested'.
8. Create notification for all admins: type 'assignment_suggested'.
9. Return created suggestions.
```

### C. Atomic Equipment Allocation (`equipmentService.js`)

```javascript
async function allocateEquipmentAtomically(equipmentObjectId, holderId, eventId, festId, expectedReturnTime) {
  // Step 1: Atomic conditional update — only succeeds if status is currently 'available'
  const updated = await Equipment.findOneAndUpdate(
    { _id: equipmentObjectId, status: 'available' },
    { $set: { status: 'allocated', currentCustodianId: holderId, updatedAt: new Date() } },
    { new: true }
  );

  // Step 2: If null, another request got there first
  if (!updated) {
    const current = await Equipment.findById(equipmentObjectId)
      .populate('currentCustodianId', 'name email');
    throw new ApiError(409,
      `Equipment ${current.equipmentId} is no longer available. ` +
      `Current status: "${current.status}". ` +
      (current.currentCustodianId
        ? `Currently held by: ${current.currentCustodianId.name} (${current.currentCustodianId.email}).`
        : 'No current custodian on record.')
    );
  }

  // Step 3: Create the assignment tracking record
  const assignment = await EquipmentAssignment.create({
    festId, equipmentId: equipmentObjectId, eventId: eventId || null,
    assignedHolderId: holderId, status: 'allocated',
    allocatedAt: new Date(), expectedReturnTime
  });

  // Step 4: Write audit log
  await auditService.log({
    actorId: holderId, action: 'EQUIPMENT_ALLOCATED',
    targetEntity: { entityType: 'Equipment', entityId: equipmentObjectId },
    changes: { before: { status: 'available' }, after: { status: 'allocated', holderId } }
  });

  return { equipment: updated, assignment };
}
```

**All other FSM transitions follow the same pattern:** check current status, update atomically, create audit log.

async function createNotification({ recipientId, type, title, message, relatedEntity }) {
  const now = new Date();
  const hourKey = `${now.getFullYear()}${String(now.getMonth()+1).padStart(2,'0')}${String(now.getDate()).padStart(2,'0')}_${String(now.getHours()).padStart(2,'0')}`;
  const dedupKey = `${type}_${relatedEntity?.entityId}_${hourKey}`;

    await Notification.create({ recipientId, type, title, message, relatedEntity, dedupKey });

  }
}

## 9. Equipment State Machine

**Valid states:** `available`, `reserved`, `allocated`, `checked_out`, `return_pending`, `maintenance`, `lost`

```
available
  ├── reserve()               → reserved
  └── allocate()              → allocated   (atomic — concurrency-safe)

reserved
  ├── allocate()              → allocated
  └── cancel()                → available

allocated
  ├── checkout()              → checked_out
  └── cancel()                → available

checked_out
  └── initiateReturn()        → return_pending
  NOTE: Event cancellation does NOT trigger initiateReturn. Gear stays checked_out.

return_pending
  ├── confirmReturn(ok)       → available
  └── confirmReturn(damaged)  → maintenance

any_state
  ├── reportDamaged()         → maintenance
  └── reportLost()            → lost

maintenance
  └── restoreFromMaintenance() → available
```

**Camera and SD card independence:** Camera return and SD card return are separate API calls on separate Equipment documents. The server must NEVER assume returning a camera also returns an SD card.

**Validation in every transition function:**
```javascript
if (equipment.status !== expectedCurrentStatus) {
  throw new ApiError(400, `Invalid state transition. Equipment ${equipment.equipmentId} is currently "${equipment.status}", expected "${expectedCurrentStatus}".`);
}
```

## 10. Footage State Machine

### SD Card Handover States

```
not_yet_handed_over
  └── initiateHandover()      → handover_pending

handover_pending
  ├── confirmHandover()       → handed_over  (currentCustodianId updates to acceptor)
  └── cancelHandover()        → not_yet_handed_over
```

**Critical rule:** `handoverNotes` is a text field for human notes. Saving or updating notes does NOT change `handoverStatus`. Only `POST /footage/:id/confirm-handover` changes it.

### Backup States

```
backup_pending
  └── updateBackup(backed_up) → backed_up

backed_up
  └── verify()                → verified  (only if no open issues)
```

### Verification States

```
unverified
  └── verify()                → verified  (BLOCKED if any issue.isResolved === false)

verified
  └── flagIssue()             → issue_recheck_required  (issue added to issues[])

issue_recheck_required
  └── resolveAllIssues() + verify() → verified
```

**Block rule for verify():**
```javascript
const hasOpenIssues = footage.issues.some(issue => !issue.isResolved);
if (hasOpenIssues) {
  throw new ApiError(400, 'Cannot verify footage. Resolve all open issues first.');
}
```

## 11. 8 Edge Case Behaviors

### Case 1: Delayed Event Conflicts With Member's Next Assignment

**Trigger:** `POST /fests/:festId/events/:eventId/delay` is called.

**Server behavior:**
1. Update `event.status = 'delayed'`, fill `event.delayInfo`.
2. Load all `approved` EventAssignments for this event.
3. For each assigned member: find their next EventAssignment starting before `delayInfo.newEndTime`.
4. If conflict found: create notification (type: `schedule_change`) to their senior and all admins.
5. Do NOT automatically reassign anyone. Require explicit `POST /assignments/:id/reassign`.
6. Original assignment preserved. Replacement adds entry to `reassignmentHistory`.
7. AuditLog: `EVENT_DELAYED`, then `ASSIGNMENT_REASSIGNED` when actioned.

**Test:** Assign member M to Event A (9–10 AM) and Event B (10–11 AM). Delay A to end 10:30 AM. Assert: notification sent to senior, assignment unchanged, both events still have M's assignment record intact.

---

### Case 2: First-Year Member Has No Senior Mentor

**Trigger:** During `POST /assignments/suggest` or `POST /assignments/:id/approve`.

**Server behavior:**
1. If member.seniority === '1st_year' and no senior is in the selected team: set `isMentorNeeded: true`.
2. On approval: if isMentorNeeded is true, send notification to all seniors and admins.
3. Dashboard query surfaces: `EventAssignment.find({ isMentorNeeded: true, status: 'approved' })`.
4. `POST /assignments/:id/assign-mentor` sets `mentorId` and clears `isMentorNeeded: false`.
5. A junior assignment without a mentor cannot be marked as `actuallyContributed: true` by the system.

**Test:** Create suggestion for 1st-year member alone. Approve it. Assert `isMentorNeeded === true` and notification created. Assign mentor. Assert `isMentorNeeded === false`.

---

### Case 3: Same Camera Needed at Two Simultaneous Events

**Trigger:** Second `POST /equipment/:id/allocate` attempt while camera is already allocated.

**Server behavior:**
1. Atomic guard: if `equipment.status !== 'available'` → 409 Conflict.
2. Sequential feasibility check via `GET /equipment/:id/sequential-feasibility?event1Id=&event2Id=`:
   - Check if `event2.startTime >= event1.endTime + venue.travelBufferMinutes`.
   - Return `{ feasible: bool, bufferAvailableMinutes: N, shortfallMinutes: N }`.
3. If short coverage exception needed, admin records override reason.
4. Pre-use checklist required at each checkout.

**Test:** Allocate CAM-01 to Event A (9–10 AM). Attempt allocate to Event B (9:30 AM). Assert 409. Attempt allocate to Event C (10:30 AM with 15-min buffer). Assert 200.

---

### Case 4: Event Cancelled After Equipment Checkout

**Trigger:** `POST /fests/:festId/events/:eventId/cancel` while EquipmentAssignment.status === 'checked_out'.

**Server behavior:**
1. Update `event.status = 'cancelled'`, fill `event.cancellationInfo`.
2. Do NOT change any EquipmentAssignment status. Equipment stays `checked_out`.
3. Send notification (type: `event_cancelled`) to event seniors and admins: "Equipment still checked out — arrange return."
4. Member can still submit `POST /coverage/unplanned` for separate coverage.
5. Both cancellation record and separate coverage record are preserved independently.

**Test:** Checkout CAM-01. Cancel the event. Assert `Equipment.status === 'checked_out'`. Assert cancellation notification sent. Assert EquipmentAssignment unchanged.

---

### Case 5: Camera Returned But SD Card Still With Photographer

**Trigger:** `POST /equipment/CAM-01/return` called. `POST /equipment/SD-05/return` NOT called.

**Server behavior:**
1. CAM-01: `status → 'available'`, `currentCustodianId → null`.
2. SD-05: unchanged, stays `checked_out`, `currentCustodianId` stays on photographer.
3. Dashboard shows SD-05 as overdue/pending independently.
4. FootageRecord.handoverStatus remains unchanged.
5. Photographer can update `handoverNotes` text at any time — this does NOT change handoverStatus.
6. Only `POST /footage/:id/confirm-handover` changes handoverStatus.

**Test:** Return CAM-01. Assert `CAM-01.status === 'available'`. Assert `SD-05.status === 'checked_out'`. Assert FootageRecord.currentCustodianId still points to photographer.

---

### Case 6: SD Card Corruption or Backup Failure

**Trigger:** `POST /footage/:footageId/flag-issue` with `{ issueType: 'corruption', description: '...' }`.

**Server behavior:**
1. Append issue object to `FootageRecord.issues[]` with `isResolved: false`.
2. Set `FootageRecord.verificationStatus = 'issue_recheck_required'`.
3. Send notification to seniors and admins: type `footage_issue`.
4. `POST /footage/:id/verify` is blocked: checks `issues.some(i => !i.isResolved)` → throws 400.
5. Recovery: `POST /footage/:id/resolve-issue/:issueIndex` sets `isResolved: true`.
6. Once all issues resolved: verify endpoint succeeds.

**Test:** Flag corruption. Attempt verify → assert 400. Resolve issue. Attempt verify → assert 200. Assert `verificationStatus === 'verified'`.

---

### Case 7: Member Covers Extra or Unplanned Event

**Trigger:** `POST /coverage/unplanned`.

**Server behavior:**
1. `reportedBy` = `req.user._id`. This is never taken from the request body.
2. `actualContributors` array must list all contributors explicitly. Reporter is not auto-added.
3. If `eventId` provided: link to existing event, `isUnplanned = true`.
4. If no `eventId`: store in `unplannedDetails`. Admin can link later to a new event.
5. `validationStatus = 'pending_review'` until approved by senior/admin.
6. On approval: all members in `actualContributors` get this coverage in their history.
7. Original EventAssignment records for anyone else assigned to the event are untouched.

**Test:** Submit unplanned report with contributors A and B (reporter is C). Validate as senior. Assert both A and B have CoverageRecord. Assert C is not listed as contributor unless explicitly in actualContributors.

---

### Case 8: Two Coordinators Request Same Camera Simultaneously

**Trigger:** Two concurrent `POST /equipment/:id/allocate` requests.

**Server behavior:**
1. First request: `findOneAndUpdate({ _id, status: 'available' })` → succeeds → 200 OK.
2. Second request: Same query → MongoDB returns null (status is now 'allocated') → 409 Conflict.
3. 409 response body includes: equipment ID, current status, custodian name and email.
4. Frontend shows: "Camera CAM-01 has just been allocated by [Name]. Please choose a different camera."

**Test:** `Promise.all([axiosPost('/allocate', body), axiosPost('/allocate', body)])`. Assert exactly one 200 and one 409. Assert Equipment has exactly one active EquipmentAssignment. Assert Equipment.status === 'allocated' with one custodian.

    }

## 14. Security Implementation Checklist

Each item must be verified before Phase 8 signoff:

1. HTTP-only JWT cookie: `httpOnly: true, sameSite: 'strict', secure: true` (production only; `false` for local dev).
2. CORS: only `process.env.FRONTEND_ORIGIN` allowed. `credentials: true` set.
3. Helmet: `app.use(helmet())` in server.js for security headers.
4. Rate limiting: `express-rate-limit` on all auth routes (max 10 req/15 min per IP) and import endpoint (max 5 req/min per IP).
5. Input validation: all request bodies validated through Zod schemas. Unknown fields stripped.
6. MongoDB injection: `express-mongo-sanitize` strips `$` and `.` from request body and query params.
7. RBAC on every route: every protected route calls `requireRole` or `requireMinRole`. Frontend button hiding is cosmetic only.
8. Firebase verification: always call `admin.auth().verifyIdToken(idToken)` server-side. Never trust client role claims.
9. Environment secrets: all `.env` files in `.gitignore`. `firebase-service-account.json` in `.gitignore`. No secrets in code.
10. Audit log integrity: AuditLog collection has no PATCH or DELETE routes. Only `auditService.log()` writes to it.
11. File upload safety: multer enforces `.xlsx` MIME type and 5MB file size limit before handing to importService.
12. Error responses: never expose stack traces in production. ApiError carries safe public messages only.
13. Concurrency: equipment allocation uses atomic `findOneAndUpdate` with status guard. No client-side locks.
14. Structured logging: replace all console.log with morgan (HTTP) and winston (application errors) in Phase 8.
